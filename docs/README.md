# ECHO ROOM ドキュメント案内

このディレクトリは、『ECHO ROOM / 残響室』の企画、要件、技術、グラフィック、実装計画を集約する正本である。

新しく作業を始める人またはエージェントは、最初に本書を最後まで読み、作業内容に対応する資料へ進むこと。

---

## 1. プロジェクト概要

『ECHO ROOM / 残響室』は、Web上で遊べる一人称短編脱出ゲームである。

- 2D画像のレイヤー、視差、接写、画面遷移によって疑似3D空間を表現する。
- 3Dモデルや自由移動する3D空間は使用しない。
- 舞台は2039年の地下研究施設、実験室E-01。
- 中心となる仕掛けは、発話文と声紋特徴量を含む通信PACKETを20分前へ送る《ECHO BUFFER》。
- 想定プレイ時間は初見20〜30分、ヒント利用時15〜25分。
- ストーリー、探索、会話、所持品、端末、主要10問の謎解きから構成する。

物語の核心を含むため、公開用資料へ本ディレクトリの内容を転載する際はネタバレに注意すること。

## 4. 作業別ルーティング

### 4.1 ストーリー・謎・台詞を扱う

必読:

1. `base.md`
2. `requirements.md`の5章、7章、8章、15章
3. `implementation-plan.md`の4章、5章、11章

確認事項:

- 大きな真相を追加しない。
- すべてを20分の時間差へ収束させる。
- 冒頭と終盤のPACKET文言を一致させる。
- 通信相手を露骨な黒幕として演出しない。

### 4.2 ゲームを実装する

必読:

1. `requirements.md`
2. `technical-design.md`
3. `implementation-plan.md`
4. 実装対象に関係する`graphics-production.md`の章

開始位置:

- `docs/progress.md`がなければ、`implementation-plan.md`のP0から開始する。
- 存在する場合は、未完了の最上位作業パッケージを確認する。
- 本番素材がなくても、同じIDと寸法のCanvas製代替素材で進める。
- Definition of Doneを満たした作業は、契約に従って適切な単位でローカルcommitする。

### 4.3 グラフィックを制作・生成する

必読:

1. `graphics-production.md`
2. `graphics-generation.yaml`
3. `requirements.md`の6章、8章、9章
4. `technical-design.md`の7章、13章、14章

固定事項:

- 基本的にSVGを作成・使用しない。
- 高解像度ラスター原本からWebPまたはPNGへ書き出す。
- 確認画像や比較出力などの一時制作物はプロジェクトルートの`tmp/`へ集約する。詳細は`graphics-production.md`の5.4節に従う。
- 生成画像に正確な文字、数字、ロゴを焼き込まない。
- 基準画像を承認してから、参照編集で別視点と差分を作る。
- 同じ部屋や機械を独立したtext-to-imageで作り直さない。

### 4.4 UI・アクセシビリティを扱う

必読:

1. `requirements.md`の9章〜13章
2. `technical-design.md`の7章、10章、15章
3. `quality-up-plan.md`
4. `implementation-plan.md`のP2、P5、10章

固定事項:

- 字幕、端末、所持品、設定はReactのHTML UIを基本とする。
- 可変UIはHTML/CSS、必要な時間変化はCanvasで表現する。
- 音声なし、キーボードのみ、動き軽減でもクリア可能にする。
- 重要情報を色、音、動きの一種類だけに依存させない。

### 4.5 保存・進行・パズルを扱う

必読:

1. `requirements.md`の6章、7章、13章〜16章
2. `technical-design.md`の6章、8章、9章、11章、12章
3. `implementation-plan.md`のP2、P3、P5、10章、11章

固定事項:

- XStateをゲーム進行の唯一の正解とする。
- UIやPixiJS objectから進行状態を直接変更しない。
- パズル判定は描画や音声から独立した純粋ロジックにする。
- XStateの内部snapshotをそのまま保存しない。
- 20分経過は即ゲームオーバーにしない。

### 4.6 テスト・リリースを扱う

必読:

1. `requirements.md`の15章、16章
2. `technical-design.md`の14章、17章〜21章
3. `implementation-plan.md`のP6〜P8、9章〜16章

固定事項:

- 検証していない作業を完成扱いにしない。
- 正規ルートだけでなく、誤答、再試行、再開、無音、keyboardを確認する。
- publicへの公開、push、Pull Request、release tagは明示的な許可後に行う。

## 5. 仕様の優先順位

資料が矛盾する場合は、次の順で判断する。

1. 依頼者の最新の明示的な指示
2. `requirements.md`の体験・受け入れ条件
3. `technical-design.md`の技術制約
4. `graphics-production.md`と`graphics-generation.yaml`の素材制約
5. `quality-up-plan.md`のUI品質方針
6. `implementation-plan.md`の工程と実行方法
7. `base.md`の細部

原案の真相と結末は、技術上の都合で変更しない。重大な矛盾は独断で解消せず、`implementation-plan.md`の停止条件に従う。

## 7. 重要な固定条件

- Web上で動く一人称短編脱出ゲーム。
- 2D素材による疑似3D表現。
- 3Dモデルは作らない。
- SVGは原則使用しない。
- 画像は高解像度ラスター原本を基本とする。
- プレイ人数は1人。
- バックエンド、アカウント、オンライン保存を設けない。
- マイク入力を必須にしない。
- 結末や主要パズルを勝手に変更しない。
- 本番素材待ちで実装を止めない。
- 作業は検証し、適切な区切りでローカルcommitする。
- push、公開、課金を伴う操作は別途許可を得る。

## 8. 文書更新ルール

- 同じ仕様を複数資料へ詳しく複製せず、本書から正本へ案内する。
- 資料の役割を越える詳細は、対応する正本へ記載する。
- 実装と仕様に差が生じた場合は、差を放置せず同じ作業内で整合させる。
- 重要な設計変更は`docs/decisions/`へ理由を残す。
- 作業進捗は本書ではなく`docs/progress.md`へ記録する。
- 新しい資料を追加した場合は、本書の資料一覧とルーティングを更新する。
- 固定条件や受け入れ条件を変更した場合は、影響するテストも更新する。
