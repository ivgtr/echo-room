# 『ECHO ROOM / 残響室』要件書

## 1. 文書情報

本書はWeb上で遊べる一人称短編脱出ゲーム『ECHO ROOM / 残響室』の体験、機能、受け入れ条件を定める。原案は`docs/base.md`、実装境界は`docs/technical-design.md`を正本とする。

## 2. 作品概要

2039年の地下研究施設E-01で、プレイヤーは「隣室の人物」から届く通信PACKETを頼りに脱出する。終盤で相手が20分後の主人公自身だと分かり、最後はプレイヤーの操作で冒頭の通信を20分前へ送る。

| 項目 | 要件 |
|---|---|
| ジャンル | 一人称短編脱出ゲーム / SFミステリー |
| 想定プレイ時間 | 初見20〜30分、ヒント利用時15〜25分 |
| プレイ人数 | 1人 |
| 舞台 | 地下研究施設の実験室E-01 |
| 中心ギミック | 発話文と声紋特徴量を含むPACKETを20分前へ送るECHO BUFFER |
| 真相 | 協力者は20分後の主人公自身 |
| パズル数 | 主要パズル10問 |

大きな真相は増やさず、通信相手を黒幕として演出しない。真相は説明だけでなく、最終送信操作によってプレイヤー自身に完成させてもらう。

## 3. 体験目標

1. 閉鎖空間を自分の視点で調べる没入感。
2. 別の場所で得た情報がつながる納得感。
3. 協力者への信頼が違和感、発見、自己認識へ変化する体験。
4. 過去の理解を後半の推理へ再利用する手応え。
5. 自分の操作が冒頭を成立させていたと分かる驚き。

## 4. 対象プレイヤー

脱出ゲームに不慣れな人から軽い論理パズルを好む人までを対象とする。専門知識、音の聞き分け、高度な反射操作、複雑な3D空間把握は求めない。

## 5. ゲーム全体の進行

| 段階 | 目安 | 主な出来事 | 認識変化 |
|---|---:|---|---|
| 導入 | 0〜3分 | 覚醒、封鎖、謎の通信 | 隣室の誰かと協力する |
| 設備復旧 | 3〜8分 | 電源経路、搬送波、保守ロッカー | 設備の規則を理解する |
| 時間差 | 8〜13分 | ログ指紋の照合 | 通信元は正確に20分後 |
| 前提崩壊 | 13〜17分 | 通信配線の追跡 | 隣室はなく、回線は自室へ戻る |
| 未来通信 | 17〜21分 | PACKET復元、時系列照合 | 未発生の情報が届いている |
| 本人判明 | 21〜24分 | 声紋特徴量の校正 | 発信者は主人公自身 |
| 因果完成 | 24〜30分 | 会話再構成、送信窓設計、本送信 | 自分が冒頭の協力者になる |

## 6. 基本体験要件

### 6.1 一人称探索

- 4方向の2D広角画像、接写、レイヤー、画面遷移で疑似3D空間を表現する。
- 3Dモデルや自由歩行を前提としない。
- 画面端、左右キー、スワイプで方向転換できる。
- 背景上の対象を直接操作し、キーボードでは同じ対象へ意味のある名前で到達できる。
- 調査対象、戻る手段、現在の操作可能状態を把握できる。

### 6.2 調査と資料

- 操作には短い視覚・文章・効果音の反応を返す。
- 進行に必要な対象をpixel huntingへ依存させない。
- 取得済み資料、重要会話、PACKET、現在の目的をSYSTEMから再確認できる。
- 正確な文字、数字、波形補助、図面はHTML/CSSまたはCanvasで表示する。

### 6.3 所持品

- ドライバー、職員カード、室内・通信配線の二層図を扱う。
- ロッカー解錠後に三点を取得し、詳細と用途をSYSTEMから確認できる。
- カード使用やドライバー使用そのものはパズルとして数えない。

### 6.4 端末

- 壁面端末はSYSTEM、LOG、SIGNAL、SECURITYの4項目を持つ。
- SYSTEMは搬送波、因果会話、最終送信を扱う。
- LOGは別順の受信・送信ログとPACKET指紋を扱う。
- SIGNALはPACKETフレーム、本文、声紋特徴量を扱う。
- SECURITYは室内図と通信配線層を扱う。
- 利用可能でない操作には理由を示す。

## 7. パズル要件

### 7.1 共通方針

- 主要パズルは10問とする。
- 各問は原則として、証拠収集、関係推理、設備への適用と検証を持つ。
- その画面だけの指示を上から押せば解ける構造を避ける。
- 正解に必要な情報はゲーム内で取得・再確認できる。
- 誤答は状態を破壊せず、世界内の理由を返して再試行可能にする。
- 総当たり、同じ操作の長い反復、専門知識を正解手段にしない。
- 時間値のように、表示結果から自明な内容を改めて入力させない。
- 音、色、動きの一種類だけに依存しない。
- パズル画面へ、解法、必要証拠、答えに直結する規則をまとめて表示しない。
- パズル画面は装置の現在値と入力部を中心とし、規則や対応表は室内、資料、会話、別の端末項目へ分ける。
- 正解後は次の場所を命令文で示すのではなく、設備の変化や新しい記録の発生をNarrativeで知らせる。
- 再開時と迷ったときだけ、SYSTEMの現在目的と段階式ヒントから調査対象を再確認できる。

### 7.2 Puzzle 1：非常電源経路

- 容量7 UNIT、各設備の消費量、ドア線の短絡痕を示す。
- ドア線を隔離し、端末、インターホン、BUFFERの順に給電すると成功する。
- 音高順パズルと音高視覚補助は使用しない。

### 7.3 Puzzle 2：搬送波同期

- 基準波と三回線の同期点を表示する。
- 早い波形は右、遅い波形は左へ補正する規則を資料から確認できる。
- A右2、B補正なし、C左1で成功する。
- 波形の横軸と位相の読み方を後続問へ再利用する。

### 7.4 Puzzle 3：保守ロッカー

- 数字錠と時刻0237を廃止し、四つの保守記号錠とする。
- 点検順と回路銘板を別の証拠として提示する。
- 二重線、環、三角、節点で解錠し、三所持品を得る。

### 7.5 Puzzle 4：通信ログ照合

- RECEIVEとSOURCEを別順で表示し、各行に三節の指紋を持たせる。
- 指紋一致によって三組を対応させる。
- 完了後に端末が全組共通の20分差を自動表示する。
- 20分という数値自体は入力させない。

### 7.6 Puzzle 5：通信経路追跡

- 室内図と通信配線層の二層を照合させる。
- 線種と端子記号を維持して経路を追う。
- 正解は通信実線、環端子J-2、ECHO BUFFER RETURNとする。
- 隣室不存在と回線の帰還を同じ推理の結果として示す。

### 7.7 Puzzle 6：PACKETフレーム復元

- HEADER、本文、VOICEPRINT、CHECKに分断された断片を提示する。
- 開始・終端記号と隣接端の連続性からC、D、A、Bへ並べる。
- 復元後に固定された4本文を確認できる。

### 7.8 Puzzle 7：時系列矛盾

- 4本文とプレイヤーが経験した出来事を対応させる。
- PACKET 04だけが未発生の赤い送信ボタンを知ると特定させる。
- 単なるPACKET閲覧や確認ボタンでは進行させない。

### 7.9 Puzzle 8：声紋特徴量の校正

- 発話音声を再生せず、職員記録とPACKETの三特徴を視覚表示する。
- 間隔を1/2、包絡を上下反転、位相を左2へ補正する。
- 自動解析スイッチと98%、99%、100%だけの進行を廃止する。
- 正しい校正結果としてE-01 OCCUPANTと主人公写真を示す。

### 7.10 Puzzle 9：因果会話の再構成

- PACKET番号ではなく、過去側の反応と設備状態を根拠に4文を並べる。
- 正しい本文と順は原案の冒頭台詞と完全に一致させる。

### 7.11 Puzzle 10：最終送信設計

- 4本文を冒頭の4受信窓へ割り当てる。
- 全PACKET共通の`-00:20:00`と`ECHO BUFFER RETURN`を設定する。
- 三条件を満たすまで送信READYにしない。
- 赤いボタンは検証後の本送信に限定し、ボタン押下自体をパズルとして数えない。

## 8. ストーリー・演出要件

- 冒頭と最終送信の4本文を一致させる。
- 相手が知る情報は、20分前の主人公が経験した範囲に限る。
- 協力者は親切で少しぶっきらぼうに描き、悪意を強調しない。
- 電源復旧、20分差、回線帰還、未来PACKET、本人一致、因果完成を段階的に示す。
- 最終送信後に冒頭会話を現在側から再演し、ドアを解錠する。
- 20分経過はゲームオーバーにせず、予備電源へ移行して進行可能にする。
- ゲーム内日本語は短く自然な文を基本とし、一文で複数の操作を指示しない。
- 専門語や英語の設備名は世界観に必要なものだけ残し、初出時には平易な日本語を添える。
- 操作案内と誤答文は抽象語だけで済ませず、見る場所や見直す条件を具体的に示す。
- 平易化によって、正解に必要な証拠、推理の段階、伏線を削らない。

## 9. ビジュアル要件

- 2D素材による一人称・疑似3D表現を維持し、3Dモデルを使用しない。
- SVGを原則としてグラフィック素材に使用しない。
- ホラー廃墟ではなく、事故直後も稼働中の研究施設として描く。
- 正確な図、文字、数値、波形は背景画像へ焼き込まず、HTML/CSSまたはCanvasで合成する。
- 波形は色だけでなく線高、節点、数列、ラベルで識別可能にする。

## 10. UI要件

- 通常HUDはバッテリーとSYSTEM入口を中心に簡素化する。
- 方角タブ、矩形調査ボタン、常時目的表示を使用しない。
- 調査時は接写へ寄り、動き軽減時はクロスフェードに置き換える。
- 字幕・通信・発見は共通Narrative UIを使用する。
- モーダル中は背景探索を無効化し、閉じた後は起点へフォーカスを戻す。

## 11. サウンド要件

- 台詞の発話音声を使用しない。
- 環境音、操作音、文字送り音、通信ノイズ、設備効果音だけを使用する。
- 音をOFFにしても情報、正誤、進行、演出結果を理解できる。
- SOUND設定はmaster、effects、environmentの単一境界で管理する。

## 12. アクセシビリティ要件

- マウス、タッチ、キーボードのみの各操作で最後まで進行できる。
- 全操作要素に意味のある名前、フォーカス表示、十分なタッチ領域を持たせる。
- 波形には同等の数列・短長表現を併記する。
- 色だけで正誤や選択状態を示さない。
- 動き軽減、字幕サイズ、字幕背景、文字速度を設定できる。
- SYSTEM、所持品、ヒント、端末から探索へフォーカスを安全に戻す。

## 13. 保存・再開要件

- XStateのdomain contextだけを保存し、内部snapshotを保存しない。
- 10問の完了ID、現在段階、所持品、誤答回数、ヒント、アクティブ時間、予備電源を保存する。
- 新しい進行schema v3だけを受理し、旧7問形式の移行層を持たない。
- 非対応・破損データは上書きせず、確認付きで進行だけ削除できる。
- 設定は進行と別keyに保存し、進行削除後も維持する。

## 14. 対応環境

- 現行の主要デスクトップ・モバイルブラウザを対象とする。
- 横画面を基本とし、320px以上で操作不能にならない。
- WebGL、Web Audio、localStorageが利用できない場合は安全な案内を表示する。
- バックエンド、アカウント、オンライン保存を設けない。

## 15. テスト要件

- 10問すべてについて正解、誤答、再試行、純粋判定をunit testする。
- 冒頭からendingまで10問を通る正規ルートをE2Eで確認する。
- keyboardのみ、touch、無音、動き軽減、focus trapと復帰を確認する。
- schema v3の全checkpoint、再開、破損・非対応保存を確認する。
- 初見プレイテストで所要時間、詰まり、偶然正解、ヒント使用箇所を記録する。

## 16. 完成受け入れ条件

1. タイトル、導入、主要10問、本送信、エンディングを通してプレイできる。
2. 旧音高順、0237ロッカー、自動VOICE ANALYSIS、単純な最終並べ替えが残っていない。
3. すべての主要パズルをゲーム内証拠だけで、無音かつkeyboardのみでも解ける。
4. 20分差、回線帰還、未来PACKET、本人一致、因果ループがプレイヤーの推理結果として示される。
5. 進行不能、取り逃し、重複会話、保存破損を起こさない。
6. 自動検証に合格し、初見プレイ時間を実測して難易度を調整している。
